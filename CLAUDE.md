# About photo-store

## What it owns

`:8329`, loopback only. What is known about the user's own photos and videos: where each original is (`source_machine`, `source_path`; the originals never leave that machine), when it was taken and how far to trust that (`date_source`: `exif`, `filename`, `mtime`, `message`, `upload`, `unknown`), where (GPS, when the file has it), a thumbnail, and a description. Ids are `photo_000001`, registered in kanban-store's entity-type registry as type `photo`, so a timeline item or a note cites a photo as a chip. **These are private photos**: dash is the front door, and nothing here is copied to noteboard. `CONTRACT.md` is the route table.

# How it works

## Imports and descriptions

Photos arrive from the machine that holds the originals: a helper there reads each file's EXIF, makes a JPEG thumbnail and writes `index.jsonl` beside the thumbnails; `~/bin/photo-import -dir <dir>` posts them to `POST /imports`, upserting by the original's `sha256`. **An import never touches a description or tags**, so re-importing after a move only updates where the original is. A description is written with `PATCH /photos/{id}` and must say who wrote it (`described_by`). Every update, import change, delete and restore first copies the whole row to `photo_revisions`; nothing is hard-deleted, and a deleted photo's thumbnail still serves so a citation keeps drawing. The one exception is `POST /photos/{id}/purge`, for a picture that must not be kept (an ID, a card, a document): it deletes the thumbnail file and blanks the description everywhere, the photo stays deleted, and imports skip it from then on. Photos sent in the user's chats come from multichat with `photo-import-messages` (rooms of at most `-max-members` members, never Discord server channels, plus the user's own servers' saved attachments with `-discord-archive`); their `source_path` is the `message_…` ref they came in and their `date_source` is `message`. `-room <room id>` (repeatable) imports one room the user named whatever its size, Discord server channels included, filing a Discord channel's photos under `discord/<server>/<channel>` as archive images are; use it for the live log after a fetched archive, since live rows carry no Discord message id and the archive import skips their images. `-discord-direct-messages <archive>/discord/direct-messages` and `-facebook-messages <export>/your_facebook_activity/messages` (with `-chats=false` to skip multichat) import the images from fetched Discord DMs and a Facebook Messenger export, each cited by the journal-store transcript of the day it was sent (found by the Discord message id or the file name, `JOURNAL_STORE_URL`), under folders `discord/direct-messages/<chat>` and `messages/facebook/<chat>`. `~/bin/photo-import-facebook -activity <export>/your_facebook_activity -source-machine <host>` imports the photos of the user's Facebook posts, albums and uncategorised photos (folders `facebook/posts`, `facebook/albums/<album>`, `facebook/uncategorised`), dated when posted (`date_source` `upload`); a post's photo is cited by that post's journal-store entry (tag `facebook-post`, found by file name), any other by its path in the export on `-source-machine`. `internal/importbatch` (hash, thumbnail, batched POST) and `internal/journalcitation` (find the entry citing a token) are shared by both commands. Which machines and folders this host's photos came from is not in this repo: see the noteboard note tagged `photo-store`.

## Faces and who is in a photo

A face model finds the faces on each thumbnail and `POST /face-scans` keeps them (`face_000001`: a box in fractions of the thumbnail and an embedding, the model's description of the face, stored normalised so two faces' cosine similarity is their dot product); `face_scans` records every scan, an empty one too, and `GET /face-scans/pending?model=` lists what is left. A photo is scanned once per model, so a face id keeps meaning one face. `face-finder/find_faces.py` is the scanner: it only measures, with InsightFace's `buffalo_l` models (licensed for non-commercial use), run from a venv outside the repo, several workers splitting photos by id number. Who is in a photo is `photo_people` (`photo_person_000001`): a people-store `person_…` id, never a name, with the face it is, a status (`suggested`, `confirmed`, `rejected`), a confidence, markdown evidence with chips, `proposed_by` and `decided_by`. `POST /photo-people` only moves a suggestion upward and answers a confirmed or rejected link as it stands, so **no matcher undoes a person's rejection**; `PATCH /photo-people/{id}` is a person's decision, and keeps the old row in `photo_person_revisions`. `GET /photos?person=` lists the photos a person is confirmed in, and `GET /people-counts` counts them. Tags stay topic words; people are links.

`photo-match-people` (`cmd/photo-match-people`, decisions in `internal/peoplematching`) proposes the links. It reads every face, the confirmed links, and each photo's context: a `message_…` source's room members in multichat when the room has at most 8, else only its sender, and the `person_…` chips of a citing transcript, each turned into a person through people-store's `GET /identities/resolve`, with `-operator` counted in every small chat. A face close to a person's confirmed faces (`ConfirmSimilarity`), clearly closer than to anyone else (`MinimumMargin`) and named by the context is **confirmed**; close but not named is **suggested**; and for a person the context names who has no confirmed face, the face that recurs across their chat photos (`ClusterInContext`) is suggested as them — **only photos whose context names them alone besides the operator**, and never a face already linked to anyone, because in a group chat the recurring face is one member's and the context does not say whose (on 2026-10-28 one group chat's face was suggested as six people). `-seed-person` with `-seed-photos` and `-seed-decided-by` confirms, on photos a person said they are in, the face that recurs across them. `-model-check N` then shows up to N suggestions, surest first, to a model that can see (`-model-role`, through llm-bridge-server's `POST /oneshot` with images): the face beside the three confirmed faces of the person most like it, with each photo's year. **A person with no confirmed face is skipped until one is confirmed by hand**: faces only suggested as someone agree with each other whoever they are, and on 2026-10-28 that confirmed a child as their mother and a baby as theirs, so 784 confirmations were returned to suggested. "same" confirms, "different" rejects, "unsure" leaves it, and its reason is added to the evidence. A link whose evidence already holds a model's answer is not asked again; a failed call is logged and skipped, and five in a row stop the run. Settings are `MatchPeopleSettingDefinitions`; `deploy.sh` installs it.

# Working in this repo

## Build, test and deploy

Module `github.com/kayushkin/photo-store`, root package `photostore`, server `cmd/photo-store`, importer `cmd/photo-import`. No build tags. Every variable it reads is declared once in `settings.go` with llm-bridge `servicesettings` (hence `replace ../llm-bridge`), served at `GET /settings`; `TestEveryEnvironmentVariableTheServiceReadsIsDeclared` fails on an undeclared `os.Getenv`. `./deploy.sh` runs the shared deploy gate, tests, checks the running unit's environment, installs `photo-store` and `photo-import` to `~/bin`, restarts the user unit and fails unless `/health` is ok and the port is bound to loopback only. Tests use synthetic bytes: **no real photo belongs in this repo.** `./generate-ts.sh` renders `photo.go` and `vocabulary.go` to `ts/model.ts`, published source-only as `@kayushkin/photo-store-types` (`file:../photo-store/ts`); bridge-ui's photo chip reads it.

## Public repository: nothing personal

This repo is meant to be public. Nothing about the user's own data goes in it — not in code, tests, comments, commit messages or this prompt: no machine names, folder or file paths of their photos, names of people or chats, account names, home directories or tokens. Tests use made-up machines and folders (`laptop`, `Pictures/Camera`). A fact an agent here needs about this host's photos goes in a noteboard note tagged `photo-store`.
